# TM95STAT.VXD — alpha 12, эксперимент для Windows 95 OSR2

**Успешная загрузка/работа драйвера в настоящей Windows 95 ещё не подтверждена.** Пользовательская система —
4.00.950 B. Сборка, статическая проверка и x86-эмуляция не подтверждают работу
реального загрузчика/VKD/VMM в этой системе.

## Что реализовано

- LE VxD с DDB первым в единственном locked-объекте. DDB вынесен в отдельный
  object-файл, чтобы переменные состояния Watcom не оказались перед ним.
  Проверка сборки отклоняет неверный порядок.
- Alpha 12 перепаковывает LE после Watcom: дисковые страницы по 512 байт,
  данные с границы 4096 байт, число предзагружаемых страниц равно числу страниц
  объекта. У объекта флаги 0x2047, класс LCOD и нет IOPL; поле OS/2 autodata
  обнулено. Экспорт ordinal 1 — прямой 32-битный адрес DDB в объекте 1.
  Эти свойства сверены с готовым динамическим WinIo 2.0 для Win95.
- В Open Watcom loadflat.c счётчик num_preload оставлен нулевым с пометкой NYI.
  Предыдущая проверка пропускала это: эмулятор сам отображал весь payload.
  Теперь проверяются дисковая структура, счётчик и точные встроенные ресурсы.
  Post-link пересобирает таблицы страниц и перемещений, включая отрицательное
  смещение во второй странице при пересечении границы указателем.
  Машинный код основного драйвера побайтно совпадает с alpha 11.
- CreateFile вызывается с CREATE_NEW. Использовавшийся в alpha 11 IOPL
  не помог загрузке и снят по сравнению с готовым динамическим драйвером.
- Загрузка через CreateFile/DeviceIoControl. В alpha 10 файл называется
  `TM95STAT.VXD`, совпадая с именами LE-модуля и DDB. Уникальность обеспечивается
  отдельным временным каталогом; случайный basename `TM9xxxx.VXD` больше не
  используется. GetShortPathNameA преобразует полный путь в DOS 8.3.
- Перед открытием устройства файл читается обычным ReadFile до конца и побайтно
  сверяется с ресурсом EXE. При ошибке 2/3 открытия по полному пути загрузчик
  пробует форму `\\.\TM95STAT.VXD` из временного каталога. Рабочий каталог
  восстанавливается до запроса к драйверу, работы с INI или показа UI.
  На всех завершённых путях удаляются только созданные нами файл/каталог.
- При отказе загрузки показывается этап и код Windows. В рабочем каталоге
  создаётся `taskmgr95-vxd.log`: GetVersion, этап, код, полный путь файла,
  имя устройства, размер ресурса, число проверенных байтов и ошибки открытия
  по полному пути/только имени. Неудачная запись отчёта не меняет исходный код.
- Время VMM и число свободных/системных страниц.
- Экспериментальный перехват Ctrl+Alt+Del и резидентный режим диспетчера.

**ОЗУ/CPU отдельных процессов, handles и сетевые метрики пока не реализованы.**
Это ещё не VxD «со всеми недостающими фичами». Он не выдаёт оценку размера куч
или EXE за расход ОЗУ и не читает структуры Win98 по непроверенным смещениям
на Win95. Для общего CPU по-прежнему отдельно пробуется PerfStats
`KERNEL\\CPUUsage`; при недоступном источнике — Н/Д.

## Контрольная диагностика загрузки

Если основное устройство не открылось с error 2/3, но файл побайтно проверен,
начиная с alpha 11 приложение дописывает в тот же журнал:

- `VWIN32 open error`: открытие уже существующего системного устройства без IOCTL.
- `Probe open error`: загрузку отдельного минимального TM95TEST.VXD.
- `Probe query attempted/error`: был ли вызван IOCTL и получена ли правильная сигнатура.
- `Probe readback bytes/device`: размер прочитанного контрольного файла и форму открытия.

TM95TEST включён как RCDATA/216. Его DDB/DIOC ABI общий с основным драйвером;
он принимает DIOC_OPEN/CLOSE, а IOCTL 1 возвращает 8 байт: size и magic 0x39354d54.
Контрольный код не устанавливает перехваты/таймеры, не вызывает VMM и не
считывает процессы. После проверки закрываются handle и временные файл/каталог.
При отказе самого контрольного открытия IOCTL не вызывается — поле attempted = 0.
Проверки не включают Ctrl+Alt+Del или автозапуск и не скрывают исходную ошибку.

Если VWIN32 открывается, а контрольный VxD не загружается, это сужает поиск к
динамической загрузке/LE, а не к измерению памяти или фильтру клавиатуры.
Открытие и ответ контрольного VxD при отказе основного требуют сравнения
основного образа/инициализации. Диагностика не является доказательством причины
без журнала настоящей Win95.

## Ctrl+Alt+Del

Включение: Параметры → «Заменять Ctrl+Alt+Del (резидентно)». Опция сначала
загружает VxD и включает фильтр, затем записывает только собственное значение
`Taskmgr95.CtrlAltDel` в `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`.
Команда автозапуска: полный путь EXE в кавычках с аргументом `/resident`.
Проверять из постоянного каталога приложения, поскольку этот путь сохраняется.
Никакие TASKMAN.EXE, SYSTEM.INI или системные бинарники не заменяются.

- VMM Hook_Device_Service подключает фильтр VKD_Filter_Keyboard_Input
  (`0x000d0012`, CL = scan code). Обработчик находится в locked-коде.
- Обработчик IRQ не выделяет память, не хранит указатели приложения и не
  вызывает USER32. Он увеличивает счётчик; таймер приложения опрашивает VxD
  раз в секунду и восстанавливает/активирует окно.
- Перехваченный make-код Delete превращается в break-код. Переданный ранее
  префикс E0 при этом нормально завершается, без повреждения состояния VKD.
  Учитываются левые/правые Ctrl и Alt, повторы и последовательность Pause.
- Второе отдельное нажатие за две секунды пропускается штатному обработчику.
  Если приложение не обновляло heartbeat более трёх секунд, нажатие также
  пропускается. Это не гарантирует восстановления после зависания самого ядра.
- Heartbeat работает и при паузе счётчиков. Подменой владеет один device handle;
  другой клиент не может её выключить. Закрытие handle снимает перехват.
- Если VMM отказывает в снятии цепочки, драйвер выключает перехват и отклоняет
  динамическую выгрузку, чтобы в цепочке не остался указатель на освобождённый код.

При включённой подмене крестик скрывает окно, процесс продолжает обслуживать
сочетание. Повторный запуск EXE активирует существующее окно. «Файл → Выход»
завершает процесс и снимает перехват; запись автозапуска сохраняется.
Для отключения подмены **и автозапуска** снять ту же опцию в Параметрах.
При отключении самого VxD опция также отключается.

Режим отключён по умолчанию. На NT/Wine включение отклоняется до извлечения
драйвера и изменения автозапуска.

## Наблюдение на реальной Win95

Пользовательский скриншот и журнал alpha 9 на 4.00.950 B подтвердили запуск
GUI и отказ открытия VxD: GetVersion C0000004, CreateFile VxD (8.3), error 2,
путь `\\.\C:\WINDOWS\TEMP\TM9xxxx.VXD`, ресурс 1557 байт.
Это исключило длинный путь в данном случае, но не подтвердило причину отказа
загрузчика. Alpha 10 устраняет расхождение имени и отдельно проверяет чтение
файла/форму открытия. Журнал alpha 10 подтвердил совпадение всех 1557 байт, error 2 при полном
пути и при `\\.\TM95STAT.VXD`. Исправления имени/пути сами по себе не помогли.
Журнал alpha 11 подтвердил: VWIN32 open error = 0, основной VxD и TM95TEST
получают error 2, Probe query attempted = 0. Все 1557 байт основного и 631 байт
контрольного файла прочитаны обратно. Отказ происходит при динамической загрузке,
до IOCTL; это не ошибка запроса памяти или включения фильтра клавиатуры.
Alpha 12 исправляет описанную выше дисковую структуру обоих образов.
Размеры новых файлов: основной 5109 байт, контрольный 4335 байт.
Успешная загрузка настоящим VMM всё ещё требует проверки в VM.

## Протокол 3

IOCTL 1: без входного буфера, выход 32 байта:
`size, version, capabilities, uptime_ms, free_pages, system_pages, cad_events, cad_armed`.
Capabilities: uptime = 1, страницы = 2, возможность включения CAD = 4.
Проверяются версия, длина и необходимые capability-биты.
Число системных страниц не подменяет объём установленной RAM.

IOCTL 2: вход 12 байт `size, version, enable` (0/1), без выходного буфера.
Включение может вернуть ERROR_NOT_SUPPORTED, если VMM не установил фильтр.
Конфликт владельца/невозможность снять фильтр — ERROR_BUSY.
DIOC_OPEN = 0; DIOC_CLOSEHANDLE = 0xffffffff.

## Проверка в VMware

Сначала снимок VM; начать с загрузки без подмены клавиш.

1. Закрыть старый диспетчер через «Файл → Выход», перезагрузить Win95 в VM,
   чтобы исключить оставшийся в памяти образ, и запустить именно alpha 12. Включить «Экспериментальный VxD». Если ошибка
   осталась, сохранить `taskmgr95-vxd.log` и новый текст ошибки с этапом.
2. Если загрузка успешна, проверить uptime/свободные страницы, отключение и
   повторное включение. ОЗУ процессов остаётся Н/Д — эта capability отсутствует.
3. Включить замену Ctrl+Alt+Del. Послать сочетание **через меню VMware**, чтобы
   оно попало гостевой системе. Скрытое/свёрнутое окно должно восстановиться.
4. Проверить отдельное повторное нажатие, NumPad Del, левые/правые модификаторы,
   обычный Delete, Pause и отпускание клавиш. Отключение возвращает штатный диалог.
5. Проверить автозапуск, повторный запуск EXE, крестик, «Файл → Выход» и удаление
   автозапуска через отключение опции. Не удалять EXE до отключения автозапуска.

## Основания ABI и проверки

Структура DDB, DIOC, номера служб VMM и соглашение Hook_Device_Service сверены с
[JHRobotics/vmdisp9x](https://github.com/JHRobotics/vmdisp9x).
ABI фильтра VKD и ordinal 0x12 сверены с VKDPHYS.ASM/VKD.map в
[примере VKD Windows 95](https://github.com/Mike1978uk/win95-intel-inboard-386pc/tree/master/custom_vkd/src).
Форма CREATE_NEW также используется в
[JHRobotics/smp.vxd](https://github.com/JHRobotics/smp.vxd).
Текущая дисковая структура сверена с готовым WINIO.VXD из
[WinIo 2.0](https://github.com/starofrainnight/winio/releases/tag/2.0):
512-байтные страницы, выравнивание данных 4096, заполненный preload, LCOD,
нулевой autodata и прямой 32-битный экспорт DDB. IOPL у locked-кода там отсутствует.
Источник незаполненного счётчика —
[Open Watcom loadflat.c](https://github.com/open-watcom/open-watcom-v2/blob/master/bld/wl/c/loadflat.c).
Сторонний код и DDK в этот проект не включены.

Open Watcom 2 собирает драйвер; `tools/fix_vxd.py` нормализует LE и проверяет DDB.
`make check` сверяет встроенный ресурс с собранными основным и контрольным VxD и проверяет чистую логику
клавиатурного фильтра. Дополнительная проверка машинного кода при изменениях VxD:

```sh
# Не входит в обычную проверку и не является зависимостью приложения.
python3 -m pip install unicorn
python3 tests/vxd_emulation.py
```

В том же коротком Wine UI-сценарии alpha 10 проверяется production-код загрузчика
с настоящими файлами: совпадение имени, побайтное чтение, открытие только по
имени после отказа полного пути, отказ при повреждении, оба отказа и очистка
с восстановлением рабочего каталога. В alpha 11 также проверяются CREATE_NEW, оба исхода контрольной загрузки,
сохранение первичной ошибки и журнал диагностики. Win9x GetVersion и граница открытия
устройства/IOCTL моделируются; это не загрузка VxD под Wine.

В эмуляторе исполняется настоящий LE-код, а службы VMM моделируются: DIOC ABI,
проверки буферов, цепочка фильтров, heartbeat, повторное нажатие, владелец и отказ
выгрузки. **Это не выполнение драйвера в Windows 95.**

В alpha 12 загрузка в эмуляторе учитывает 512-байтные дисковые страницы,
предзагрузку и перемещения на обеих сторонах границы. Повторная упаковка обоих
образов побайтно неизменна. Отдельно подтверждено, что старая alpha 11
отклоняется новой проверкой счётчика предзагрузки. Это проверки структуры,
а не доказательство совместимости с загрузчиком Win95.
